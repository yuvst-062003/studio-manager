── What it fixes ─────────────────────────────────────────────────────────────────────
`POST /dev/demo/reset` works once and then answers 500 for ever.

Three decisions meet, and each is right on its own:

  * `audit_log` is in `NEVER_WIPED` (app/services/demo/service.py) — it is append-only by
    grant, and §19.4 logs every persona switch to it, so it is evidence rather than
    scratch data.
  * `person` IS wiped: the `personas` fixture layer deletes and recreates the nine rows.
  * `fk_audit_log_actor_person_id_person` is ON DELETE RESTRICT.

So the first audit row carrying an `actor_person_id` pins the person it names, and the
next wipe raises RestrictViolation. Measured on 2026-08-26: with an empty `audit_log` the
reset answers 200, and 200 again with no actions in between; one `POST /locations` (which
writes no audit row) leaves it at 200; one `PATCH /studio` (which writes one, with an
actor) takes it to 500. Truncating `audit_log` restores it.

That makes §19.7's "restores the fixture set from a versioned seed" unreachable after a
single meaningful use — for a developer pressing the dev bar's reset button as much as for
a test. `e2e/fixtures/global-setup.ts` currently clears `audit_log` before every run and
prints a paragraph saying so; when this lands, delete `clearAuditLog()` from that file and
the E2E suite can go back to resetting per test.

── Why SET NULL and not something else ───────────────────────────────────────────────
The alternatives were weighed:

  * Wiping `audit_log` too — no. §11.2 makes it append-only BY GRANT: the app role holds
    INSERT and SELECT and nothing else, so the service cannot delete from it even if we
    wanted that, and §19.4's switch trail is the evidence an impersonation feature in a
    system holding medical data about minors has to leave.
  * Not wiping `person` — no. The personas layer has to be able to restore them.
  * CASCADE — no, and emphatically. It would delete audit rows as a side effect of a demo
    reset, which is the one thing the append-only grant exists to prevent.

SET NULL keeps the row, the action, the timestamp and the diff, and loses only the link to
a person who no longer exists. An audit entry whose actor has been deleted is exactly what
"the actor is gone" should look like. `actor_person_id` is already nullable — plenty of
rows carry NULL today (every `dev.sign_in_as`, which records `actor_identity_id` instead).

`actor_identity_id` gets the same treatment for the same reason. `auth_identity` is not
wiped today, so it is not currently reachable — but it is the same shape of trap, and
leaving one of a matched pair fixed is how the next person rediscovers this.
"""
