## What M1 inherits — eight open holdbacks

Read them from `docs/plan/state.yaml`, or run `./scripts/cockpit.sh` and look at the
**next** tier. They are, by kind:

**Carried debt — four obligations M0.4 handed over, each with a test already written that
goes red until met.** Two of them carry a failure message telling you to delete the test at
that point.

1. `auth_identity.is_developer BOOLEAN NOT NULL DEFAULT false`, settable only by seed or
   migration. `tests/restrictions/test_04_the_flag_is_not_grantable.py` is vacuous until
   this column exists.
2. Set `request.state.is_developer` and `request.state.studio_is_demo` from the verified JWT
   and the resolved studio. The rule is already wired into
   `app/core/tenancy.py::studio_id_from_request` and is correct — only its inputs are absent.
3. Move `personas` out of `PLANNED_LAYERS` in `app/services/demo/fixtures.py` into a real
   `FixtureLayer` — the nine §19.3 personas.
   `test_no_layer_is_both_planned_and_present` fails if the planned entry is left behind.
4. The role switcher: `POST /dev/act-as/{person_id}`, `acting_as_person_id` on the session,
   the `X-Acting-As` response header, and an audit entry per switch (§19.4). Register it into
   the `dev-bar` slot with `registerDevTool` — **the container is not reopened.**

**Carried debt — one from M0.2.**

5. The staging api still connects as the **superuser**, not `studio_app`. Railway's managed
   Postgres provides one role, so both DSNs point at the same superuser and the append-only
   audit grant is not actually in force on staging. M1 closes it by giving `studio_app` a
   login password from a Railway secret. Recorded in `docs/deploy/railway-runbook.md`.

**Conflict.**

6. **C3** — M3's trial booking needs a health declaration that §14 puts in M4.
   `health_form_template.kind` is already `(full|trial)` in §4.3. **Seed the `kind='trial'`
   template here**; that is what unblocks M3 without pulling M4 forward.

**External — blocked on you.**

7. SPEC §15 item 7 — studio branding. Per D1, v1 is **logo only**; there is no colour
   customization to collect.

8. **`HB-domain` — SPEC §15 item 5, the stable HTTPS domain. Repointed from M0 to W1 on
   2026-08-25, and this is the milestone where it stops being cosmetic.** `up.railway.app`
   is on the Public Suffix List, so the app hosts and the api host are different **sites**,
   not just different origins. §11.7's `httpOnly/SameSite` refresh cookie is third-party
   across them and Safari drops it, so an iPhone parent's session dies at the 15-minute
   JWT expiry and cannot renew. Local dev will not show you this — `localhost:5173 →
   localhost:8000` differ only by port, and port is not part of a site.

   **The trap, stated plainly: do not move the refresh token to IndexedDB to make staging
   work.** It contradicts §11.7 and is strictly weaker — an XSS can read IndexedDB and
   cannot read an httpOnly cookie. If staging auth fails cross-site, that is this holdback
   reporting itself, not a bug in your code. Build the cookie as §11.7 specifies, verify it
   on `localhost`, and escalate for the domain. The full reasoning and the target subdomain
   layout are in `infra/railway/README.md` § The domain.

## Two things the tooling now expects

- **`docs/plan/state.yaml` is the machine-readable plan state.** Tick pieces in the same
  commit as the work. Never write anything measurable into it — no test results, no branch,
  no environment health. Those are computed, and a declaration that contradicts a measurement
  is how a status board stops being trusted.
- **`./scripts/cockpit.sh`** serves a local dashboard on `127.0.0.1:7317` — the active wave,
  the holdbacks tiered by distance, environment health, and buttons for every gate. It reads
  the repo; it never writes to the prose docs.
