# W5 lane GATES — E2E harness implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement
> this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close W2's, W3's and W4's E2E exit gates by building a seed-and-authenticate
fixture over the §19.4 dev routes, mounting the screens the flows walk, and rewriting the
five spec bodies against what the apps actually expose — with no `test.fixme` left.

**Architecture:** Three layers, built bottom-up. (1) A fixture package under `e2e/fixtures/`
that resets the demo studio, signs a browser context in as a §19.3 persona over
`/dev/sign-in-as`, and builds the scenario each flow needs through the product's own API.
(2) Mount wiring in the three `App.tsx` files for the feature directories that are built,
unit-tested and imported by nothing. (3) Five rewritten spec bodies addressing hash routes
and the real testid vocabulary.

**Tech Stack:** Playwright 1.62.1 (`@playwright/test`), TypeScript, Vite dev servers on
5173/5174/5175, FastAPI on 127.0.0.1:8000, PostgreSQL 18 on 127.0.0.1:55433.

**Spec:** `SPEC.md` §13 (the five flows), §5.10 (money), §10.3/§10.5/§10.6 (offline),
§5.6 (schedule), §5.4a (funnel), §19.3–19.7 (demo studio and dev tools).
Holdbacks: `docs/plan/state.yaml` → `HB-w2-e2e-gate`, `HB-w3-e2e-harness`.

## Global Constraints

- Python tooling is `.venv/bin/` prefixed. A bare `python3`/`pytest` is an old 3.8.
- `retries: 0` stays. A flake in flows 2 and 3 is a finding, not something to re-run.
- Never deep-link past the thing under test. Deep-link to the screen the flow starts on.
- Never rename an existing `data-testid`. Add only, and only where one is genuinely missing.
- No router library. Hash routing already works (`useHash` / `useHashRoute`).
- No hardcoded port in a spec. Origins come from `e2e/origins.ts`.
- The redirect is never proof of payment. Assert on the IPN settling the ledger (§5.10 step 5).
- All money in agorot, integers. Timestamps stored UTC, rendered `Asia/Jerusalem`.
- No inline Hebrew in a component — everything through `web/packages/i18n`.
- Logical CSS properties only.
- A spec that cannot be made to pass is a bug report, never a `test.fixme()`.
- Do not touch: `alembic/versions/**`, `app/schemas/**`, `app/models/__init__.py`,
  `app/main.py`, `web/packages/{ui,core,api-client,i18n}/**`, `app/services/comms/**`,
  `web/apps/*/src/features/comms/**`.

## Findings that shape this plan

Established against the running stack before planning, not inferred.

**F1 — `/dev/demo/reset` works once, then 500s for ever. BLOCKING.**
`audit_log` is `NEVER_WIPED` (append-only by grant, and evidence — `app/services/demo/service.py:32`),
`person` is in `wipe_plan()`, and `fk_audit_log_actor_person_id_person` is `ON DELETE RESTRICT`.
So the first audit row carrying an `actor_person_id` makes every later reset raise
`RestrictViolation`. Reproduced minimally: empty `audit_log` → reset 200; reset again → 200;
`POST /locations` (not audited) → reset 200; `PATCH /studio` (audited, actor set) → reset **500**;
`truncate audit_log` → reset 200. The fix is a migration (`ON DELETE SET NULL` on
`actor_person_id` and `actor_identity_id`) or running the wipe as `studio_migrator` — both
outside this lane. **Task 0 records the decision taken.**

**F2 — The demo fixture set seeds no scenario.** `app/services/demo/fixtures.py` has three
layers: `studio`, `personas`, `health_templates`. `PLANNED_LAYERS` still owes structure,
students, health, attendance, money and belts. So "seed over the dev routes" means: reset for
a clean slate and the nine personas, then build the scenario through the product API. That is
not a second seeding path — it is the product.

**F3 — A persona can only become a guardian through §5.4a's trial booking.** The nine demo
personas have no `email` and no `phone`. `StudentService.add_guardian` and
`RegistrationService.approve` both re-derive an already-known guardian by *address*
(`match_person(email, phone)`), so for a persona they match nothing, create a duplicate
Person, and issue an invitation with no recipient → `ck_invitation_invitation_has_a_recipient`
→ **500**. `TrialService` is the one path that attaches `Guardian(person_id=parent.id)` by id.
The fixture therefore books through `POST /trial-bookings/self` and converts.
This also means **E2E-1's approval step 500s as written** — see Task 12.

**F4 — The demo studio's payment step has no simulator branch.** §19.6 says a demo studio
"gets no payment form at all, and its payment step renders §19.5's IPN simulator instead".
The backend half exists (`409 demo_studio_has_no_live_form`). `PaymentsScreen.pay()` has no
demo branch: it calls `client.orderForm()`, catches, and renders `common.error.generic`. The
order *is* created first, so the ledger half of E2E-3 is reachable — but the screen a parent
sees after pressing שלם is a generic error. Asserting over that would be writing a green test
across a bug.

**F5 — `scripts/e2e-backend.sh` cannot find the database from a worktree.** It probes with
`docker compose exec -T db`, and compose derives its project name from the directory, so in
`../sm-e2e` the container of project `studio-manager` is invisible: `service "db" is not
running`, exit 1, and the whole `webServer` block dies. Every lane runs in a worktree.

**F6 — `pytest` runs against the same database as the E2E stack.** `tests/conftest.py` reads
`settings.DATABASE_URL`. A backend test run — this lane's or lane COMMS's — writes into the
database a live E2E run is asserting against.

**F7 — The dev bar's IPN simulator hardcodes `expectedAmountAgorot: 32000`**
(`web/packages/ui/src/dev-bar/IpnSimulatorTool.tsx:44`), and `build_ipn_query` sends that value
as the amount. It can only ever settle a ₪320 order. That file is in the do-not-touch set, so
the specs fire the IPN over `POST /dev/upay/simulate-ipn` instead — which is the honest shape
anyway: an IPN is uPay's server-to-server callback, not a user action.

**F8 — The refresh cookie is not port-scoped.** It is host-only on `localhost`, path
`/api/v1/auth`. `localhost:5173`, `:5174` and `:5175` share one jar, so two personas cannot be
signed in inside one `BrowserContext`. Cross-app flows use one context per persona.

`persona person_id values are NOT stable across a reset` — the personas layer recreates the

```ts
import type { APIRequestContext } from '@playwright/test'
import { API_ORIGIN } from '../origins'

export type PersonaKey =
  | 'owner' | 'manager' | 'lead' | 'assistant'
  | 'parent3' | 'parent1' | 'trial' | 'both' | 'none'

export type Persona = {
  key: PersonaKey
  person_id: string
  studio_id: string
  label: string
  roles: string[]
  is_guardian: boolean
}

/** §19.7. Restores studio + the nine personas + both health templates, and nothing else —
 *  every scenario this suite needs is built on top through the product's own API. */
export async function resetDemoStudio(request: APIRequestContext): Promise<void> {
  const response = await request.post(`${API_ORIGIN}/api/v1/dev/demo/reset`, { data: {} })
  if (!response.ok()) {
    throw new Error(`demo reset failed: ${response.status()} ${await response.text()}`)
  }
}

export async function personas(request: APIRequestContext): Promise<Record<PersonaKey, Persona>> {
  const response = await request.get(`${API_ORIGIN}/api/v1/dev/personas`)
  const body = (await response.json()) as { items: Persona[] }
  return Object.fromEntries(body.items.map((p) => [p.key, p])) as Record<PersonaKey, Persona>
}
```

- [ ] **Step 4: Write `e2e/fixtures/auth.ts`**

```ts
import type { BrowserContext } from '@playwright/test'
import { ORIGINS } from '../origins'
import type { AppName } from '../origins'
import type { PersonaKey } from './api'

/**
 * §19.4's switcher, entered from a URL. Hit through the APP's own origin, never the API's:
 * the refresh cookie is host-only, so a cookie set on 127.0.0.1:8000 is invisible to a page
 * on localhost:5174.
 *
 * The cookie is NOT port-scoped — one jar covers all three app origins — so one context
 * holds exactly one persona. A cross-app flow uses one context per person, which is what it
 * actually is.
 */
export async function signInAs(
  context: BrowserContext,
  persona: PersonaKey,
  app: AppName,
): Promise<void> {
  const response = await context.request.get(
    `${ORIGINS[app]}/api/v1/dev/sign-in-as/${persona}`,
    { params: { app, return_path: '/' }, maxRedirects: 0 },
  )
  if (response.status() !== 307) {
    throw new Error(`sign-in-as ${persona} answered ${response.status()}: ${await response.text()}`)
  }
}
```
