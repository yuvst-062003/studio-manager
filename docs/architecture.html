§8.1a Data storage

Four stores, each with a job the others cannot do — and a recorded reason for each, so none of these gets re-litigated later.

System of record
PostgreSQL 16

Everything durable. Chosen for reasons specific to this product, not generic preference.

Ephemeral only
Redis

ARQ job queue, rate-limit counters, refresh-token denylist, short caches. Nothing here survives a wipe, and nothing needs to — every job is re-derivable from Postgres.

Client side
IndexedDB via Dexie

Cached rosters and the pending_ops queue in the staff app.

Files
Object storage

Signed health PDFs, photos, logos, export bundles — reached only through short-lived signed URLs. No bucket is ever public.

Why Postgres, specifically

  • The money ledger requires ACID. A payment allocated across four charges either lands entirely or not at all. Eventual consistency here produces “we charged them twice” bugs — expensive to unwind in a community where everyone knows each other.
  • Multi-row atomic transactions are the core operation, not an edge case. Approving a registration writes Person + Student + Guardian + Enrollment + HealthDeclaration + consents in one commit. A belt-exam pass writes the result, creates the belt row and updates current_belt_id together. Half of either is corruption.
  • Referential integrity is the cheapest correctness available. The database refuses a charge pointing at a non-existent student, so the code doesn't have to remember to.
  • JSONB exactly where the shape is genuinely unknown — form templates, audit diffs, studio settings, notification payloads — without surrendering relational guarantees everywhere else.
RejectedWhy
MongoDB / FirestoreThe ledger is inherently relational and needs cross-document transactions. Firestore's query limits would push us to denormalize names into charge documents — which destroys the anonymization design rule and makes deletion impossible
SQLiteConcurrent writers, multi-tenant isolation, managed PITR backups
A separate OLAP storeReports run fine against indexed queries and a read replica. Revisit past ~50 studios, not before
A search enginePostgres full-text is more than enough for “find a student by name”
localStorage for offline5 MB cap, a synchronous API that blocks the UI thread, strings only, no transactions — the pending-ops queue needs atomic writes so a mark is never half-recorded when the app is killed mid-tap
Postgres BLOBs for filesThey bloat every backup and every PITR restore, and you cannot hand a browser an expiring link to a bytea column
The honest alternative

At one studio, a Postgres-backed queue (SELECT … FOR UPDATE SKIP LOCKED) would remove Redis entirely. It stays because ARQ is the chosen worker and Railway provisions it in one click — but if you ever want fewer moving parts, Redis is the one to drop, and nothing durable would be lost.

The step everyone skips

Managed Postgres PITR and object-storage versioning are configuration. A documented restore drill, run once before launch and once a year, is not. A backup you have never restored is a hypothesis, not a backup. Encryption keys live in Railway secrets, never in the database — which is the entire point: a leaked dump is inert without them.

§3–4 The spine

The single most important idea in the data model: a parent is never connected to a class or a group. They are connected to their children; their children are connected to groups. Two link tables carry the entire system.

§3.2 Roles & permissions

Two different mechanisms, which must not be conflated.

Granted by a human
Staff roles

Rows in role_assignment(person, role, scope_type, scope_id) — scoped, revocable: platform_admin · owner · manager · lead_coach · assistant_coach.

Derived, never granted
Guardian is not a role

There is no guardian role, no role_assignment row, nothing for a manager to assign. A person is a guardian because a row exists in the guardian table linking them to a child. A guardian is an ordinary user with a login and some children attached. “Adult student” likewise isn't a role — it's one Person who is both the student and their own guardian.

So in the matrix below, the guardian column is not a role's permission set — it is what applies to a person for the specific children they are a guardian of, resolved per record. “own” always means “only for my own children”.

One hard rule shapes the rest: coaches see people, never money. No charge, payment, debt or price is reachable from any coach-scoped endpoint or screen — which means you can hire a coach without exposing the club's finances.

One person, many roles

A role is a (person, role, scope_type, scope_id) tuple, so “the manager who is also the lead coach of the competitive group” is one person with one login and two role assignments — never two accounts. This is the single most common complaint about club software that models roles as a column on a user.

Four state machines carry most of the system's correctness. Each one has at least one state that exists specifically to prevent a lie.

The bulk rule

סמן הכל נוכח promotes only unmarked rows. A parent's pre-reported absence is locked against bulk actions and can only be changed by an explicit coach long-press. Without this, one tap silently erases every warning a parent gave you.

Charge & payment order

charge.status
open → settled

A charge is never mutated to record payment. It is settled when the sum of its payment_allocation rows equals amount_agorot. status is a derived cache, recomputed in exactly one place. Also: void, written_off.

payment_order.status
The one that matters

pending → paid, or failed, expired — or amount_mismatch. That last state exists because a parent can edit the form amount before submitting: real money arrives, but it doesn't match. The payment is recorded, allocated to nothing, and a manager is alerted.

A coach whose very first session is in a basement with no signal must already have the roster. If priming is lazy or best-effort, the offline feature is theatre — it works in the office and fails on the mat, which is the only place it matters.

§5.4a Trial & conversion

The public link's only job is to get someone through the door for one free lesson. Nobody enrolls themselves.

  1. 1The landing pageA public page at /t/{studio-slug} — the club's shop window, not a form. Logo, photos, what the club does, where and when, and one offer: שיעור ניסיון חינם. A per-group QR pre-selects that group.
  2. 2Sign in first, then childrenGoogle or Apple in the system browser — before any child details. Then name, birthdate and class▸group per child, with + הוסף ילד נוסף for siblings. Groups are filtered by the child's age where age_min/age_max are set.
  3. 3Short health declarationThe trial template (kind='trial') plus a drawn signature, per child. Signed before they set foot in the dojo.
  4. 4Pick the lessonThe next N upcoming sessions of each chosen group, one pick per child. Then [ הוסף ליומן ] and a downloadable .ics.
  5. 5Straight into the parent appAlready signed in, profile live, status trial. No invitation email, no waiting — one less place for the funnel to leak. The manager sees them in the שיעורי ניסיון queue immediately.
  6. 6Before the lessonParent reminded 24h ahead. The roster flags them unmistakably.
  7. 7The lessonAttendance taken exactly as normal — the trial row is just flagged. Coach can leave a note.
  8. 8Follow-upDay 1 “איך היה?” · day 3 · day 7. The 7–14 day window every buyer's guide names as decisive.
  9. 9Manager convertsPicks the group, sets the price, status → active, enrollment created. The parent then completes the full health declaration through the app gate. No conversion after N days → lost, with a reason.
Why sign-in comes before child details

The account exists the moment they authenticate, so the profile is live in the parent app when they finish — no invitation email, no waiting, one less step to abandon at. And someone who drops out after signing in leaves a Person with no children, which the parent app renders as a resume-booking prompt rather than a dead end.

§5.4 Enrollment

Two paths. Both end with a manager deciding, and with the parent — not the manager — filling in the health form.

Path A
Manager adds directly

+ תלמיד חדש → parent details → child details and group → + הוסף ילד נוסף for each sibling → save. Everything is created immediately with health_status = missing and an invitation goes out. The manager never types a health form — the parent completes it through the app gate.

Path B
Public trial → manager converts

The public URL and QR book a first free lesson only. After the trial the manager converts the lead, picks the group and sets the price. The public link is therefore a marketing asset — Instagram, a flyer QR, the club's bio — not an admin form.

§5.5 The health gate

One gate, in one place: the parent app. Nothing on the mat is ever blocked.

Where it bites
Parent app — hard block

A guardian signs in and any of their children has health_status = missing → the app routes into the declaration flow and no other screen is reachable. This is the only gate.

Where it does not
The mat — never blocked

The roster shows ⚠ הצהרת בריאות חסרה with a one-tap reminder; the parent is chased on days 1, 3 and 7; the manager dashboard lists everyone missing. The coach can still mark them present.

Why blocking attendance would be worse

Blocking a row in an app does not stop a child stepping onto a mat — the coach controls that, physically, and can simply decline to accept the child. A hard block would only stop the record from being accurate: worse data, no safer child. There is deliberately no block_attendance_without_health setting.

Changing a schedule rule rewrites only sessions in the future. Two categories are protected and never overwritten: sessions in the past (so attendance history keeps its true times), and any session with is_manually_edited = true. The change dialog shows exactly what will happen before it happens:

שינוי לוח זמנים — ג'ודו / מתחילים מ: א' 17:00–19:00 · ו' 12:00–14:00 ל: א' 17:30–19:30 · ו' 12:00–14:00 ✓ 32 שיעורים עתידיים יעודכנו ✕ 18 שיעורים שהתקיימו — ללא שינוי ✕ 2 שיעורים שעודכנו ידנית — ללא שינוי ⚠ · 15.11 אימון ים 90 דק' · 22.11 אימון משותף

Closures work the same way: the training-year setup pre-fills Israeli holidays as proposals the manager ticks, never as automatic closures — studios differ, and a wrong guess deletes real lessons. Adding a closure cancels the affected sessions and notifies the affected guardians.

§5.7 · §10 Attendance & offline sync

The single most adoption-critical feature, and the one no competitor has.

ג'ודו / מתחילים · א' 17:00 נוכחות: 22 · חסרים: 2 · לא סומן: 1 [ ✓ סמן הכל נוכח ] ✓ דנה כהן ✓ יוסי כהן ✕ נועה לוי הודיעו מראש ✓ איתי מזרחי ✕ רוני ברק ○ עמית שרון לא סומן ⚠ ליאם דוד הצהרת בריאות חסרה

Four network states, not two

The interesting failures live between “online” and “offline”. The client never trusts navigator.onLine alone — it reports true on a captive-portal wifi that routes nowhere — so mode is derived from actual request outcomes against a lightweight ping.

StateWhat it looks likeHow the app behaves
OnlineRequests succeedNormal
Slow3–15s responses, a basement with one barA 6s timeout demotes the request into the offline path rather than spinning. Never a blocked screen waiting on a slow write
IntermittentConnects, drops, reconnects. Captive portalsTreated as offline until two consecutive requests succeed, so the app doesn't thrash between modes mid-session

API down, client online5xx, or a failing health checkDistinguished from offline: “השרת אינו זמין”. Queueable writes still queue; the rest are blocked with an explanation, not a silent failure

Authentication while offline — the one that bites

The access JWT lives 15 minutes. A coach on a mat for 90 minutes will have an expired token long before they finish.

  • Offline writes never depend on a valid token. Marks go to pending_ops regardless of auth state — the local write is not an API call.
  • On reconnect the client refreshes (rotating refresh token, 30 days) and then flushes.
  • If the refresh token has also expired — a device offline over a month — the queue is preserved, not discarded. The user signs in again and it flushes afterwards, validated against the same person_id.
  • If the re-authenticated identity is a different person, the queue is not flushed — it becomes a conflict card for a manager. A device changing hands must not silently rewrite who marked what.
  • There is no code path that discards unsynced work.

Cross-actor conflicts

The interesting case isn't two coaches — it's a coach offline while a manager works online.

Coach marks a student who was unenrolled meanwhileStored, flagged, surfaced the same way
Two coaches mark the same sessionLast write by device_marked_at — except a parent pre-report, which never loses to a bulk action regardless of timestamp

Staleness & cache budget

The bootstrap payload carries synced_at and a server generation. Past 24 hours the roster header shows נתונים מ־<time> and refresh is retried on every open and foreground resume; past 7 days the cache is untrustworthy for display but the queue is still preserved and flushable. The cache is bounded to two days of sessions, evicted oldest-first — with pending_ops exempt from eviction under all circumstances. Unsynced work is the one thing that must never be reclaimed.

§5.10 Billing run

A worker job, once a month, per studio. Only the first charge is ever variable.

  1. 1Walk active enrollmentsEvery active enrollment not covered by a student_freeze gets one charge with kind = tuition for the period. Leads, trials and frozen students produce nothing — because they have no active enrollment.
  2. 2Prorate the first month onlyamount = round(monthly × remaining_sessions ÷ total_sessions_in_period) — using materialized sessions, not calendar days. The original amount and a readable proration_note are stored, so the parent sees “בגין 3 מתוך 8 שיעורים”.
  3. 3Flat thereafterClosures, holidays and absences never change the amount. The monthly fee buys the slot, not the sessions.
  4. 4IdempotentUnique on (enrollment_id, period_year, period_month, kind). Re-running creates nothing.
  5. 5Escalate what goes unpaidDay 3 a gentle reminder, day 7 firmer, day 14 a final notice plus a manager task. Aged debt (0–30 / 31–60 / 60+) on the finance report.

Calendar

A secret webcal:// feed per guardian and per coach — GET /api/v1/calendar/{token}.ics. Google Calendar, Apple Calendar and Outlook all subscribe natively, and cancellations propagate by themselves. Event mechanics
RSVP · fee · consent

Guardians answer מגיע / לא מגיע before the deadline. A fee_agorot creates a normal charge with kind = event, payable through the standard uPay flow. Belt exams
An event type, not a side feature

A lead coach nominates candidates by targeting students directly. On the day the examiner records pass/fail. §11 Privacy & security

The system holds medical information about other people's children. All six measures ship in v1 — two of them are architectural and cannot be retrofitted.

The design rule that makes deletion possible at all

No PII is ever denormalized into a financial row. Charges, payments and allocations reference payer_person_id and student_id — never a stored name. Invoices render names by join. Get this wrong on day one and “delete my child's data” becomes impossible without destroying seven years of tax records.

Two more things worth naming. Tenant isolation is enforced at the query layer — a TenantMixin applies WHERE studio_id = :current_studio by default, and bypassing it requires an explicit .with_all_tenants() escape hatch legal only in platform-admin code. And no ת.ז. is collected at all — the smallest sensitive-data footprint that still runs a club.

Enforced structurally, not by trusting the UI

Sometimes you genuinely will need to look at a studio's real data to debug something. That path exists, and it is deliberately uncomfortable:

  1. 1Request elevationFor one studio, with a typed reason and a fixed expiry — 60 minutes by default, 24 hours maximum.
  2. 2Written to the studio's own audit logNot a separate admin log. The owner sees it alongside every other access to their data.
  3. 3The owner is notified immediately“גישת תמיכה הופעלה לחשבון שלך — <reason> — עד <time>”
  4. 4Every read is logged individuallyTagged with the elevation id.
